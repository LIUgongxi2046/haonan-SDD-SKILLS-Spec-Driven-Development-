# 按业务结果开发与验证

## 选择本次输入

**首次接手或更换功能**时核对下列适用依据，建立唯一任务记录，保存已读取依据的路径和版本。

**续接同一功能**时，从原记录核对当前操作、工作目录及版本、最近有效结果和下一条检查。核实用户最新决定、未提交修改和运行环境。遇到来源缺失、版本变化、依赖变化或证据相互冲突时，重读受影响的原文并复验对应检查。项目规定每次必读的资料仍按要求读取。


1. **【当前 Task 工单】**：读取项目采用的 `implementation-tasks.md`、已有 `cursor-tasks.md` 或其他唯一任务来源中正在执行的任务项，明确“验收门禁 (DoD)”。用户指定的独立任务使用 `SINGLE_TASK`，完成本项及受影响验证；已授权的全部待办使用 `AUTHORIZED_BACKLOG`，连续完成，前置任务的独立交付检查通过后自动推进依赖满足的下一项。区分本任务交付、组合验收和 S009 独立测试，不能要求子任务先完成依赖后续实现的父功能验收。
2. **【架构规范 (@LLD / @HLD)】**：依据任务属性，读取对应的后端协议、数据 Schema 或前端组件规范，严禁瞎编字段。
3. **【界面参考】**：读取 S003 的确认设计、Token 与行为要求；用户允许时比较截图，未执行视觉检查时准确记录。
4. **【BDD 规范 (@PRD)】**：读取 PRD 第 8 节或当前项目对应的用户故事章节，作为编写测试脚本的原始依据。
5. **开发记录**。首次建立记录时读取[记录规则](../haonan-s000-pmp/references/task-development-records.md)和[正文模板](references/development-record-template.md)。后续在同一记录维护当前结果、剩余验收和证据位置。
6. **【协作接收】**：读取 S007 指定的主 Agent 与各子 Agent 的实际窗口名称、会话或 Agent ID，明确当前执行者身份。主 Agent 对应协调负责人，子 Agent 对应执行负责人；核对所属任务、允许修改范围、共享资源负责人、前置产物及版本、环境、汇报入口与集成验收责任。子 Agent 接收主 Agent 的工单和指导后核实当前文件及服务使用相应版本，冲突动作登记给主 Agent 处理，其他条件已满足的部分继续执行。身份不明确时仅暂停存在写入冲突或责任不明的动作，不自行声明为主 Agent。
7. **执行依据**。首次接手核对[共用执行规则](../haonan-s000-pmp/references/codex-execution.md)和[实施流程](references/implementation-workflow.md)。跨会话恢复任务或发生连续执行问题时读取[长任务要求](references/vibe-coding-issues.md)。
8. **【评审与测试交接】**：核对 S007 登记的 S006 评审版本、相关 `issue_id`、适用条件、修复及复核责任；未解除的必要条件只阻塞相应动作。接收本任务的开发交付检查、父功能验收关联、S009 启动条件和测试接收者。测试缺陷同时读取复现依据、实际版本、预期结果和回归范围，修复后交回 S009 复验。

前端任务同时读取页面映射、原型源码、所属 CSS、资源、全部控件与交互状态，核对批准视口及响应式要求。项目要求原型 1:1 还原时，在实施开始即纳入逐页验收。

接收前端工单时确认高保真原型版本、公共布局与组件的已验证版本、当前页面检查时点及负责人。直接复用批准原型的布局、CSS、Token、图标和资源，工程组件化保留设计细节。公共组件缺少适用检查时由所属负责人完成相应检查后扩展使用；不根据组件库默认外观自行改变批准设计。

单执行者从原工单接续当前功能，核对有效工作目录、需求依据、最近有效结果和下一项业务检查。身份分配、窗口反馈及定时监督条款仅在实际委派时使用；用户另行指定的监控要求持续有效。多执行者协作按[实施流程](references/implementation-workflow.md)接收责任、约定检查时间并跟踪结果。主 Agent、子 Agent 指研发执行者，业务 Agent 使用设计中的 identifier。

主 Agent 在获准协作开始时核实状态查询、消息接收、继续任务、运行操作观察及会话续接方式，登记实际能力和最近检查依据。接收检查输入、直接及间接依赖、失效条件、共同检查负责人及 S009 独立执行要求；项目级视觉授权与页面比较条件沿用已有有效决定。

## ⚙️ The BDD Coder Loop (四步闭环编码工作流)

逐任务执行 Given–When–Then、Red、Green、自查与 Refactor，实施过程中持续维护同一开发记录。

### 第一步：测试先行 (The Red Phase)
- **操作**：在编写业务逻辑前，检查已有 `*.spec.ts` 或 `test_*.py` 等项目测试；能够验证对应行为时直接使用，缺少覆盖时补充或创建测试。
- **逻辑**：根据 PRD 描述的 Happy Path 和异常分支，编写 Given-When-Then 断言。
- **目标**：实际运行测试，确认失败来自缺失或错误的业务行为，保存命令与断言。依赖未安装、语法错误和环境故障不能充当有效 Red 证据。已有测试能够复现时直接使用；无行为影响的修改采用相应验证，不制造失败。
- **范围选择**：按实际行为与风险选择单元、接口、集成、业务 E2E 或界面检查，保留全部必需验收。已有有效覆盖不要求重复创建文件，证据复用仍需核验对应输入和版本。

### 第二步：最小实现 (The Green Phase)
- **操作**：实现当前任务完整业务要求，同时保持修改集中。测试未覆盖的已承诺行为继续进入测试和实施范围，不能缩减为只通过现有断言。
- **原则**：
    - **数据与服务**。按批准设计验证存储范围、接口授权和外部依赖，检查数据写入后能否由预期使用方读取。
    - **Agent**：遵循批准的节点与工具定义，错误在发生位置明确报告，不使用替代响应掩盖失败。
    - **前端**：使用当前工程组件与语义化 Token，视觉比较遵守用户权限。
- **协作写入**：共享字段、迁移、规范、组件、环境或进程需要变更时，将所需结果、依据、受影响使用方和接收条件交给指定负责人。当前授权和责任均覆盖时自行处理；转移责任须完成交接并停止原执行者对应写入。
- **开发中还原**：公共布局与组件在多个页面复用前核对原型；每页形成结构与样式后立即检查并修正，业务接口绑定后检查实际内容和全部适用状态对布局的影响。已知差异在本功能开发过程中处理，不能累计为全部开发完成后的集中重做任务。当前未解决差异只暂停对应页面接收及受影响组件扩展，其他依据充分的工作继续。

### 第三步：视觉与接口自查 (Visual & Contract Check)
- **UI 校验**：验证页面操作、状态、间距、圆角和颜色规范；视觉工具获准时执行截图比较。共享组件的全部受影响页面进入回归。
- **接口校验**：核对 Response JSON、Schema、序列化映射、类型、空值和业务语义；字段变更及实现替换使用 [改动检查](../haonan-s006-review/references/change-review.md)。
- **原型还原**：按项目要求逐页核对结构、导航、栏目、宽高、间距、字体、字号、字重、行高、颜色、边框、圆角、阴影、图标、列表密度、按钮、表单、弹窗和抽屉。按相同视口及状态核查，保留加载、空白、失败、等待、只读和权限状态。实际接口消费与业务操作同时通过才能完成页面验收；视觉比较未执行时记录事实。
- **检查接收**：主 Agent 或指定接收者核验开发中检查、差异修正与当前版本证据。交付时复验发生变化或仍有问题的部分，复用符合工具条件的有效结果；不因检查时点增加而机械重复全部检查。权限未允许的视觉比较继续记录未执行，源码、DOM 和计算样式的检查结果不能冒充图像比较结论。
- **比较条件**：记录浏览器、视口、缩放、适用设备像素比、字体与资源版本、数据和交互状态。获准视觉比较覆盖完整页面及适用状态，动态内容处理不能隐藏业务断言；差异指标用于辅助定位，不单独作为 1:1 还原通过依据。未获准时保持视觉未运行，继续可执行的结构、样式与行为检查。

### 第四步：重构与交付 (Refactor & Done)
- **操作**：在测试变绿的前提下，优化代码可读性，移除冗余的调试 Log。
- **确认**：重构后再次运行对应测试；本任务明确负责的全部必需验收通过才登记 `ACCEPTED`，技术子任务的接收不能代表父功能业务完成。依赖后续 UI 的组合验收及 S009 独立测试按计划保留在对应任务中，未经执行不能登记通过。继续下一项已授权任务，提交与推送按已有具体授权执行。
- **记录完成检查**：登记 `ACCEPTED` 之前保存本任务 Markdown 中的实现依据、相关位置、实际验证及关联影响，核实需求/验收、代码与环境、证据引用和相关文档，更新项目索引。每项任务均适用，不能用会话回复或总报告代替；本任务全部必需验收通过且记录与索引完整后才能登记该任务完成，父功能业务验收范围保持完整。记录未完成时继续维护并保留实际任务状态，任务状态和证据继续引用唯一当前来源。
- **协作交付**：子 Agent 向主 Agent 及工单指定接收者提供代码与环境版本、当前产物、有效证据、完整未完成项及阻塞负责人。指定集成验收者验证组合后的用户结果，主 Agent 核验交付证据、处理剩余问题并判断整体完成；子任务通过不自动完成父功能。
- **测试接收**：用户要求全部开发完成后启动 S009 时，主 Agent 核验计划列明的整批开发任务、开发及集成检查、记录、评审条件和待测试版本，确认该批写入结束后按已有授权交给 S009。S009 自身通过不作为启动前提，父功能最终完成仍等待全部适用测试与复核。测试缺陷返回 S008 修复，由 S009 完成失败项及受影响范围复验；完整交接字段和循环见 [实施流程](references/implementation-workflow.md)。

## 🛠 开发纪律 (Execution Disciplines)

1. **无测试不编码**：绝不跳过测试直接写业务逻辑，除非是纯样式的 Dumb 组件。已有测试复用及无行为影响修改的验证按 Red 阶段执行；纯样式修改仍须完成适用界面检查。
2. **依赖顺序**：发现缺少数据库字段或 API 时在同一任务记录补充前置工作；属于已有授权范围则继续完成，真正受阻时记录原因并推进其他可执行任务。多窗口执行时同步核查写入责任，属于其他负责人的前置工作通过依赖请求推进。各窗口连续推进当前已分配且条件满足的任务，协调负责人维护完整 backlog 的覆盖和后续分配。其他窗口正在负责的任务不得重复领取；责任调整通过交接生效。单执行者承担完整任务及相应协调责任。
3. **敏感数据处理**。涉及受限数据时，依据当前项目的授权范围和数据政策验证访问、传输、日志和导出。设计要求脱敏的入口同时验证允许与拒绝路径。
4. **修改范围**：按任务需要修改相关文件，保留原有有效设计和无关用户改动，不设置妨碍完整功能实现的文件数量上限。
5. **验证安排**：修改期间执行直接相关的行为、类型和接口消费检查，交接时满足工单全部必需检查。完整工程批次由指定负责人执行，其他执行者提供所需产物和针对性证据，详见 [实施流程](references/implementation-workflow.md)。
   证据复用同时受工具能力约束：当前校验器仅支持同基线有效回执。跨基线复用须有已实现并验证的适用性复核能力，不能修改原执行回执或仅凭说明登记通过；配套设计及当前执行条件见 [实施流程](references/implementation-workflow.md)。
   变更影响按 `check_id` 及实际输入和使用关系判定。共同检查在输入、环境、定义及责任要求一致时由指定负责人执行，各窗口引用证据并保留任务专属检查。复核无法证明适用时执行覆盖不确定范围的检查，不反复分析相同材料；共同检查复用不免除 S009 明确要求的独立执行。
6. **进展检查**：连续两个预定进展检查时点没有新增业务验收、经过验证的阶段业务结果、必要前置产物或阻塞解除时，主 Agent 检查原因、依赖、重复读取、重复验证及责任安排。新增代码或测试数量本身不能解除此检查条件；预计交付时间到达而产物缺失时立即检查。明确处理者、下一动作、预期证据及下次检查时间并继续获准任务。正常长时间操作依据运行证据判断，检查次数本身不能作为失败依据，必要验证必须保留。
7. **主 Agent 指导与监督**：主 Agent 负责分配任务、解释需求与设计、核查子 Agent 的实际进展及验证证据，并处理依赖、共享资源和阻塞。任务接收、阶段产物、阻塞及交付均是检查时点；执行中持续跟踪状态，不能仅下发任务后等待最终回报。出现问题时给出有依据的解决方案或定位步骤，明确处理者和完成条件，检查修复结果；跨任务指导同步受影响子 Agent 并确认生效。需要亲自修改时先交接写入责任。
8. **子 Agent 执行与反馈**：子 Agent 按主 Agent 分配的工单完成实施、测试、修复和记录，在分配范围内自主处理常规问题。阶段产物、阻塞和交付及时回报主 Agent，说明实际结果、证据、剩余断言和所需协助。需要主 Agent 协调时继续条件已满足的其他部分；不得自行改变其他执行者的责任、扩大范围或新增下级执行者。主 Agent 的指导执行后回报结果，接受证据核查。
9. **按用户操作完成开发集成**。每次选择当前功能中一个可观察的用户结果，围绕它完成全部适用层次。接口、页面、命令或后台任务的正常入口一旦可用，即从该入口验证实际使用和结果。按原验收逐项完成其余操作、异常和恢复路径。切换功能遵循 S007 的调度规则。

主 Agent 同时按登记的时间主动核查状态，不能只等待子 Agent 回报。检查安排、未收到反馈时的处理、运行中操作的检查方式及监督能力限制遵守 [实施流程](references/implementation-workflow.md)，不得声称未运行的后台监督已经生效。

涉及跨任务依赖、待集成产物或工具能力的处理，主 Agent 按 [S000 持续交付流程](../haonan-s000-pmp/references/delivery-workflow.md) 指定动作和接收条件。子 Agent 核实当前输入与修改责任，执行后回报对应任务、产物版本、检查结果及实际使用方；主 Agent 核验问题是否解除。常规实现与修复在原授权及任务范围内自主进行，不增加每个步骤的确认。

最近实际检查、指导动作、负责人、预期证据及下次检查时间保存在现有任务来源，工具结果可直接引用。发送提醒不能代替问题解除；会话续接恢复运行操作及逾期检查，在授权任务完成、用户停止或真实阻塞条件出现前持续执行相应责任。

## 📑 Output Standard (输出规范)

- **工程质量**。使用当前语言和项目已约定的类型、格式和构建检查。需要说明设计意图时在对应代码处添加注释。
- **测试反馈**：实际执行工程测试、业务验收和受影响检查，保存命令、版本及结果；失败时定位、修改并再次验证，不能把应执行的检查转交用户。
- **开发记录交付**：提供本任务主记录及项目索引的实际路径。最终说明中的行为、验收范围和未完成内容与记录一致。
- **协作反馈**：子 Agent 向主 Agent 回报新增可操作功能、通过的业务验收、剩余阻塞及负责人、当前版本证据和接收条件；主 Agent 汇总核验后的整体进展、指导决定、问题处理结果及后续分配，向用户报告。任务状态继续使用项目唯一来源，测试数量作为辅助。
- **进度与消耗反馈**：使用 S007 确定的范围版本、环境、分子、分母与计算方法，分别报告业务验收比例和已实现待验收内容。阶段起止时间、经过时长及可取得的 Token 增量对应同一时段的业务结果、前置产物和阻塞处理；不可取得的数据明确标识，不填零、不重复合计。统计方法及无阶段结果时的处理见 [实施流程](references/implementation-workflow.md)。
- **反馈内容**。说明本次通过的用户操作、剩余验收及下一条检查。引用实际证据，原型、模型、工具和业务数据分别遵守既有授权。

## ⚙️ The BDD Coder Loop (四步闭环编码工作流)

### 第一步：测试先行 (The Red Phase)
-   **操作**：在编写业务逻辑前，先创建 `*.spec.ts` 或 `test_*.py`。
-   **逻辑**：根据 PRD 描述的 Happy Path 和异常分支，编写 Given-When-Then 断言。
-   **目标**：实际运行测试，确认失败来自缺失或错误的业务行为，保存命令与断言。依赖未安装、语法错误和环境故障不能充当有效 Red 证据。已有测试能够复现时直接使用；无行为影响的修改采用相应验证，不制造失败。

### 第二步：最小实现 (The Green Phase)
-   **操作**：实现当前任务完整业务要求，同时保持修改集中。测试未覆盖的已承诺行为继续进入测试和实施范围，不能缩减为只通过现有断言。
-   **原则**：
    -   **数据/后端**：严格遵守本地化存储与 Hook 拦截纪律，严禁引入未经 LLD 定义的外部依赖。
    - **Agent**：遵循批准的节点与工具定义，错误在发生位置明确报告，不使用替代响应掩盖失败。
    - **前端**：使用当前工程组件与语义化 Token，视觉比较遵守用户权限。

### 第三步：视觉与契约自查 (Visual & Contract Check)
- **UI 校验**：验证页面操作、状态、间距、圆角和颜色规范；视觉工具获准时执行截图比较。共享组件的全部受影响页面进入回归。
-   **契约校验**：确认 Response JSON 结构与 LLD 中的 Schema 100% 字节级匹配。

### 第四步：重构与交付 (Refactor & Done)
-   **操作**：在测试变绿的前提下，优化代码可读性，移除冗余的调试 Log。
- **确认**：重构后再次运行对应测试；全部必需业务验收通过才登记 `ACCEPTED`。继续下一项已授权任务，提交与推送按已有具体授权执行。

## 🛠 开发纪律 (Execution Disciplines)

1.  **无测试不编码**：绝不跳过测试直接写业务逻辑，除非是纯样式的 Dumb 组件。
2. **依赖顺序**：发现缺少数据库字段或 API 时在同一任务记录补充前置工作；属于已有授权范围则继续完成，真正受阻时记录原因并推进其他可执行任务。
3.  **医疗数据脱敏本能**：在处理任何患者信息、化验单数据时，强制检查 HLD 定义的脱敏 Hook 是否已挂载。
4. **修改范围**：按任务需要修改相关文件，保留原有有效设计和无关用户改动，不设置妨碍完整功能实现的文件数量上限。

---

## 📑 Output Standard (输出规范)

-   **代码质量**：代码必须包含清晰的注释（说明“为什么”而非“是什么”），TypeScript 必须开启严格类型校验。
- **测试反馈**：实际执行工程测试、业务验收和受影响检查，保存命令、版本及结果；失败时定位、修改并再次验证，不能把应执行的检查转交用户。
-   **交互响应**：
    -   *“测试已编写完毕，目前处于红灯状态（预期失败）。现在开始实现核心 Service 逻辑...”*
    -   *“根据您提供的原型截图，我修正了卡片的 `shadow` 和 `border-radius` 以符合 Naive UI 视觉风格...”*
    - *“当前任务的必需验收通过，证据已记录，继续执行下一项已授权任务。”*

## ⚠️ Instructions (结对编程硬约束)
1.  **拒绝过度设计**：严格按照 DoD 验收门禁执行，禁止在任务范围外添加“你觉得以后会有用”的冗余功能。
2.  **严防幻觉**：如果对某个 API 的入参结构不确定，必须强制要求读取 `@LLD` 文档，不准猜测。
3. **部署边界**：遵守用户与 HLD 已确认的本地、云端或混合存储要求，不擅自改变数据位置、供应商和网络边界。

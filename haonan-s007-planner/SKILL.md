# 实施任务规划

维护项目唯一任务表。为每项获准的业务结果确定负责人、依赖、开发入口和验收条件。按产品已有设计安排适用的工程步骤。

---

## 📥 Input Handling (Phase 0: 完整工程资产验收 Tollgate)
生成工单前核查以下适用依据。必要信息缺失时保留对应前置任务和阻塞条件，仍为全部已知承诺建立任务及验收；不得以单项未知缩减整个计划。

1. **架构依据**。核对当前操作涉及的系统边界、数据去向及授权要求。
2. **【S005 系列 LLD 规范】**：必须 `@` 出当前任务涉及的数据 (1)、后端 (2)、Agent (3) 和前端 (4) 详细设计文档。
3. **界面依据**。涉及界面时引用批准的设计、资源、交互状态和视口。已有原型包含源码、CSS、Token 或参考图时，提供对应位置。图像比较遵守项目要求和用户授权。
4. **【S002-PRD 业务要求】**：确认涉及的 BDD 验收标准与合规脱敏要求。
5. **【协作条件】**：核实用户允许的窗口或 Agent 数量、模型与工具要求、现有执行者、工作目录和共享资源责任。登记唯一主 Agent 的实际窗口名称、会话或 Agent ID，以及各子 Agent 的对应身份与任务。主 Agent 沿用用户指定或已生效的协调负责人；尚未指定时在计划中明确拟任者及依据，不能把拟分配写成已接收。根据用户授权设计分工、依赖和交接，实际启动执行者须遵守当前授权，计划使用实际可用条件，不自行增加执行者。单执行者同样使用完整工单，可以兼任相关责任。
6. **【执行依据与任务模式】**：执行前完整读取 [Codex 执行规则](../haonan-s000-pmp/references/codex-execution.md) 与 [完整任务规划与交接](references/planning-workflow.md)，核查需求分母、依赖、完成条件及授权。明确功能或缺陷使用 `SLICE`，安排完整实现与验证；已确认范围使用 `BACKLOG`，建立全部任务、依赖与验收；根据真实进展和用户决定调整待办使用 `REPLAN`，保留尚未验收的原始承诺。
7. **【已有记录与依赖依据】**：检索项目已有开发记录和知识索引，按 [开发记录](../haonan-s000-pmp/references/task-development-records.md) 为每项 S008 任务指定稳定 `task_id`、`development_record`、需求和验收 ID。使用 [设计责任](../haonan-s000-pmp/references/design-ownership.md) 判定实际依赖，使用 [决策记录](../haonan-s000-pmp/references/decision-register.md) 关联必要未知与受影响任务。
8. **【S006 评审承接】**：读取适用评审的版本、范围、决议及问题清单，将每项未关闭 `issue_id` 关联责任任务、修复产物、复核者、检查方法和证据。`CONDITIONALLY_APPROVED` 的条件逐项安排；`REVISE` 先处理受影响设计，其他依据充分的工作继续。已有复核结论核验版本后继承，不能仅凭报告存在判定可以编码；尚未要求专项评审的局部工作按实际风险说明适用性，不自动增加全项目评审。
9. **【监督执行条件】**：在协作条件中登记实际可用的状态查询、消息接收、继续任务、运行操作观察及会话续接方式。区分已经核实的能力与待执行安排，计划本身不代表监督已经运行；主 Agent 在获准执行开始时核实这些入口。工具能力不足时保留未完成责任和处理条件，不承诺未具备的后台能力。

## 🔄 Task Breakdown Strategy (实施组织与约束法则)

### 1. 功能级纵向切片 (Feature-Driven Vertical Slicing)
每份工单针对一个独立核心功能，并写出业务结果。用户要求整个模块或多个功能时，为全部功能建立工单、共享依赖和总体验收，不能只交付其中一项。

功能按用户可完成的业务操作组织，明确入口、数据与接口、页面操作、结果及后续使用。菜单与功能可以一对多或多对一，不以菜单数量代替业务范围。默认按完整功能分配开发窗口；同一功能内部前后端在输入明确时可以并行，负责人持续承担该功能的开发集成和验证。不得把全部前端页面与全部后端接口分别交给不同窗口，并将所有联调集中到项目末期。

同一交付队列默认集中开发一个功能。按业务优先级、可用输入和已有进展选择当前功能，指定一名负责人完成开发集成。用户或项目已明确授权多项并行时，按独立验收能力约定上限。挂起、切换和恢复按[规划流程](references/planning-workflow.md)执行。开发集成通过后可以领取下一项，独立测试沿用项目约定。

每项业务结果明确执行和集成责任，单执行者可以兼任。实际委派时，主 Agent 负责调度、解决共享依赖和接收结果，各执行者持续负责获分配功能的开发与验证。子任务关联原始验收 ID，父功能保留完整组合验收。

本节主 Agent、子 Agent 均指研发协作中的执行者；产品运行时负责推理、调用工具的角色称为业务 Agent，名称和 identifier 沿用产品设计，两类身份分别登记。

### 2. 核对依赖的产物与使用方

为每条会阻止开工的依赖回答三个问题：哪个操作需要它？哪项检查能证明产物可用？缺少它影响开发、组合验收还是发布？仅将必须提前验收的任务登记在 `depends_on`。对只需部分产物的情况，为可独立验收的产物指定负责人和使用方，将其余工作保留在原任务范围。

数据变更检查写入和读取，接口变更检查调用方，异步任务检查触发与结果接收，界面变更检查正常入口和适用状态。按实际使用关系安排先后。多个执行者共用文件、迁移、环境或进程时明确写入责任。

实现依赖与组合验收分别安排：子任务的交付检查必须能够在自身必要输入满足后执行；需要后续 UI 或集成才能验证的动作由对应集成任务负责，并保留原始验收 ID 的关联。`depends_on` 引用具有独立交付检查且必须先达到 `ACCEPTED` 的前置任务，遵守当前共享校验器；父功能完整验收依赖子任务和适用独立测试，子任务不得反向依赖父功能完成。仅部分产物就绪时明确其独立交付任务与接收检查，不将未验收的完整前置任务直接标记完成。

主 Agent 按 [S000 持续交付流程](../haonan-s000-pmp/references/delivery-workflow.md) 接续项目和处理跨任务问题；S007 将处理决定维护到既有计划的责任、依赖、产物与验收位置，保留用户授权和有效成果。当前项目采用的工具能力按实际入口核验，必要配套任务具有明确使用方及独立接收条件，不能仅凭通用规则假定工具已经支持。

### 3. 依赖前置与视觉依据 (Context & Visual Grounding)
- 为当前操作引用批准需求、设计和接口的具体章节，以及已有产物和验证入口。
- 每项共享资源指定唯一写入者和使用方。不同工作目录仍须核查数据库、服务和端口是否共享。共享修改由所属负责人交付，其他窗口依据接收条件使用。
- 前端任务关联确认的原型、UI Token、交互与视口；只有用户允许视觉工具时执行图像比较，其他情况下保留视觉待验收状态并执行可用的行为检查。
- 项目要求原型 1:1 还原时，逐页写入布局、样式、控件、状态、响应式和实际接口消费的验收条件，明确原型版本、页面映射及验证方式。
- 高保真原型直接作为页面实施依据；公共布局与组件投入多个页面前，完成适用视口和状态的结构、样式及行为核对。每页在结构与样式形成、业务绑定完成及交付时核验受影响部分，发现差异在当前任务内修正，不把页面还原推迟到全部功能完成后。相应检查时点、负责人、证据与受影响页面写入工单；有效结果可复用，不要求重复全部检查。
- 复用原型的布局、CSS、Token、图标和资源；转换为工程组件时保留设计中的结构、尺寸和交互，不能以组件库默认样式代替批准设计。已知差异未解决的公共组件停止向更多页面传播；其他不受影响且输入充分的任务继续。视觉工具权限保持不变，未执行的视觉比较如实记录，不能据此宣称已经验证视觉一致。
- 页面检查条件同时明确浏览器、字体与资源版本、缩放和适用设备像素比、数据状态及动态内容处理。结构、行为、视觉分别指定检查 ID 与责任阶段；沿用已有项目级视觉授权及其限制，不新增逐页确认。未授权的视觉检查保持 `NOT_RUN`，不能以源码检查代替完整视觉验收。

## 📑 Output Standard (标准工单交付模板)
> 输出采用项目约定的 Markdown 格式，可直接保存为 `implementation-tasks.md`、已有 `cursor-tasks.md` 或项目指定任务文件，并在 IDE 中执行。

每项工单填写[适用字段](references/task-template.md)，保留原始需求、全部验收、开发记录和索引。涉及受保护数据、模型和界面的复合功能，可按需查看[跨层工单示例](references/cross-layer-example.md)。

### 执行环境与依据

- **架构约束**。引用当前功能适用的系统边界、数据和设备要求。
- **微观设计规范**：`@S005-1` 至 `@S005-4` 对应的 LLD 文件。
- **视觉参考库**：[实际批准的原型与 Token 路径；视觉工具获准时读取对应图像，未执行时保留待验收状态]。
- **测试标准**：所有业务逻辑必须先行编写 BDD 测试用例。已有测试完整验证对应行为时，S008 可以直接复用；缺少覆盖时补充。
- **业务责任**。记录功能 ID、需求来源、开发与集成验收负责人。存在子任务时，关联对应的功能和原始验收 ID。
- **监督安排**。单执行者在原记录维护当前操作、检查结果和下一动作。实际委派或用户要求监督时，补充预计交付时间、检查间隔、下次检查时间与时区、反馈入口，按[规划流程](references/planning-workflow.md)核查运行状态与阻塞。
- **进度与消耗**：沿用已有统计依据，缺少依据时使用批准业务结果的验收数量比例，登记分母 ID、范围版本、环境及计算方法。分别报告已验收、已实现待验收、阻塞和未开始内容；阶段耗时与可取得的 Token 用量关联本期业务结果，不能用代码量、测试数量或窗口数量计算完成比例。详细计算和记录要求见 [规划流程](references/planning-workflow.md)。
- **协作安排**：填写可并行任务、前置产物及版本、允许修改范围、共享资源负责人、环境责任、接收条件及交接对象。调整负责人时登记当前实现、代码与环境版本、文件范围、有效证据、完整未完成项和接收者。原负责人停止对应写入，接收者确认后生效；交接完成前不得同时修改。字段要求见 [任务模板](references/task-template.md)，完整执行与检查要求见 [规划流程](references/planning-workflow.md)。协作安排维护于现有计划，任务状态继续使用唯一来源。
- **功能推进与页面检查**：填写当前未完成开发集成的功能集合、数量上限、可执行集成任务和负责人；页面填写公共组件复用前检查、开发中核对、接口绑定后核对及交付接收条件。主 Agent 依据实际产物核验，不把这些内部检查变成用户逐页确认流程。
- **评审与测试交接**：登记 S006 评审版本、`issue_id` 与责任任务；分别列出 S008 开发及开发验证、S009 独立测试、父功能最终验收的任务和检查 ID。填写 S009 启动条件、接收者、交接版本及缺陷修复后的复验责任，不将 S009 通过作为其自身启动条件。
- **检查影响与复用**：按 `check_id` 登记验收定义、源码与测试、直接和间接依赖、构建输入、环境与数据身份、失效条件及原证据。相同输入、环境、检查定义和责任要求下的共同检查指定唯一执行者，使用方引用同一证据并保留自身专属断言。S009 必须独立执行的检查明确标识，不被共同检查复用免除。判定与工具条件分别遵守规划流程及 S000 配套设计。

### 交给开发执行

从依赖满足的获准任务中选取当前功能，交付用户操作、输入位置、可观察结果和第一项检查。基础产物通过后，由实际使用方从正常入口验证。开发集成、独立测试与最终交付分别使用计划约定的验收条件。

## ⚠️ Instructions (实施官强制约束)
1. **依赖纪律**：不得跳过尚未满足的必要输入；数据、接口与状态已经明确时允许独立工作推进，最终集成仍须完成全部业务验收。
2. **绝对禁写业务代码**：你只负责输出战略级工单，不准写任何具体的 `function` 逻辑，把编码工作留给 S008。
3. **闭环验收**：每个 Task 必须包含绝对可衡量的“验收门禁 (DoD)”。
4. **协作完整性**：检查并行任务的写入责任、前置产物、接收条件和集成验收负责人，不得以窗口数量或测试数量替代业务进度。

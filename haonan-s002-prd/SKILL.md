# Haonan S002 PRD

## 定位

把业务意图转化为研发、设计、测试可共同使用的需求契约。PRD 定义“为什么、给谁、做什么、如何验收”，技术选型与部署拓扑留给 S004/S005。

## 工作模式

- `DRAFT`：从想法或不完整材料创建可评审草案。
- `UPDATE`：基于变更更新 PRD，并保留修订和影响记录。
- `AUDIT`：审查现有 PRD 的遗漏、歧义、冲突和不可测试条目。

## 输入处理

1. 读取用户提供的文件、图片、代码或现有 PRD，不重复索要已有信息。
2. 建立事实表：`EXPLICIT`、`INFERRED`、`UNKNOWN`。
3. 只有目标用户、核心目标、平台或不可逆范围差异无法判断时才暂停；其他缺口以可逆假设继续。
4. 易变化的法律、标准、竞品和依赖能力需联网核查并引用权威来源。

## 标识与追溯

为条目分配稳定 ID：

- 功能需求 `FR-###`
- 非功能需求 `NFR-###`
- 验收标准 `AC-###`
- 业务规则 `BR-###`
- 风险 `RISK-###`
- 未决问题 `Q-###`

每个 `FR` 至少关联用户/场景、业务规则和 `AC`；每个关键 `NFR` 必须包含度量方式或标记为待基线化。

## 编写步骤

1. 定义背景、目标、成功指标、非目标和范围边界。
2. 梳理角色、权限、核心对象、术语和事实来源。
3. 描述主流程、异常/恢复流程和关键状态机。
4. 用可观察行为写功能需求，避免植入数据库、框架或云服务方案。
5. 为每项功能写 Given/When/Then 或等价可测试验收标准。
6. 覆盖性能、可靠性、安全、隐私、可访问性、兼容性和可观测性等适用 NFR。
7. 建立需求—流程—页面—验收—风险追溯矩阵。
8. 记录依赖、假设、未知项、版本计划和变更影响。

## 质量门禁

- 范围内/范围外明确，没有“优化体验”一类不可验证表述。
- 正常、空、错误、权限、超时、重复提交、撤销与恢复状态按适用性覆盖。
- 权限规则包含主体、资源、动作和数据范围。
- 指标有定义、计算口径、数据源和目标；无证据时不编造阈值。
- 需求之间不存在明显冲突，术语与状态枚举统一。
- 技术建议与产品需求分栏，避免架构方案伪装成业务要求。

## 输出

使用 `references/prd-template.md` 作为结构基线，按项目复杂度删减，不机械填满。输出开头列出版本、状态、事实源、假设和缺失输入；结尾附追溯矩阵、风险、未决问题和下游交接。

状态使用 `PLANNED`、`CREATED`、`OBSERVED`、`VERIFIED`、`BLOCKED`。PRD 被写出是 `CREATED`，不等于需求已由用户批准。

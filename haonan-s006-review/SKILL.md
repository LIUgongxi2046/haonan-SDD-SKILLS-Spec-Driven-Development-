# Haonan S006 技术评审

## 定位

评审“资产之间能否正确对接”，不是单篇文档打分。允许部分输入审查，但必须声明范围与盲区，不用虚构的匹配百分比制造确定性。

## 工作模式

- `DESIGN_REVIEW`：编码前检查 PRD/HLD/LLD/原型的契约与风险。
- `RELEASE_GATE`：基于代码、测试、安全、迁移和运维证据判断能否发布。
- `PARTIAL_AUDIT`：只审查用户指定的资产或链路，不给全局 Go/No-Go。

## 输入处理

1. 读取可用资产及其版本、状态、来源和批准记录。
2. 建立审查范围、事实源和缺失资产清单。
3. 缺失不相关资产不阻塞；影响结论的盲区标记 `BLOCKED` 或限制结论范围。
4. 对标准、法规、依赖和安全要求等易变化信息，核查当前官方来源。

## 重点契约

按范围选择：

- 战略/PRD ↔ 指标、范围和验收。
- PRD ↔ 原型/UI：角色、流程、状态、权限和 AC。
- PRD/NFR ↔ HLD：性能、可靠性、安全、数据和成本。
- HLD ↔ S005：边界、所有权、协议、故障和部署假设。
- Data ↔ Backend：字段、事务、生命周期、迁移和删除传播。
- Backend ↔ Agent：工具 Schema、权限、超时、幂等和错误。
- Backend/Agent ↔ Frontend：类型、事件顺序、状态、取消和恢复。
- UI ↔ Frontend：Token、组件、资产、响应式和可访问性。
- 代码 ↔ 设计：实现偏差、兼容、迁移和技术债。
- 测试/安全/部署 ↔ 发布标准：证据、残余风险和回滚能力。
- 发布账本 ↔ 真实环境：commit、构建物校验和、数据库版本、配置变量、部署目标、客户端上传与审核状态。

详细矩阵见 `references/review-matrix.md`。

## 审查步骤

1. 为每个结论记录资产路径、版本和具体证据位置。
2. 比较字段、状态、错误、时序、权限和 NFR；区分差异与真实冲突。
3. 评估影响、发生条件、可检测性、修复成本和发布后果。
4. 分级问题并给出最小修复动作、责任 Skill、验收证据和截止门禁。
5. `RELEASE_GATE` 按 [../haonan-s000-pmp/references/release-state-contract.md](../haonan-s000-pmp/references/release-state-contract.md) 核对每个发布面；任一版本不一致时不得给全局 `GO`。
6. 复核修复后关闭问题；未复核只标记 `CREATED` 或 `OBSERVED`，不标记 `VERIFIED`。

## 严重性与决议

- `P0 BLOCKER`：可导致数据损坏、重大安全/合规风险、核心链路不可用或无法安全回滚。
- `P1 HIGH`：高概率造成核心功能/可靠性问题，应在发布前解决或由责任人显式接受残余风险。
- `P2 MEDIUM`：可控缺陷或技术债，有明确计划可带风险发布。
- `P3 LOW`：局部改进，不影响当前门禁。

`DESIGN_REVIEW` 结论：`APPROVED`、`CONDITIONALLY_APPROVED`、`REVISE`。

`RELEASE_GATE` 结论：`GO`、`CONDITIONAL_GO`、`NO_GO`、`INSUFFICIENT_EVIDENCE`。

只有审查范围足够且证据真实时才给全局结论。

发布门禁至少要求：候选 commit 冻结、工作区范围清楚、受影响测试通过、构建物可追溯、秘密扫描完成、数据迁移/备份已演练或不适用、生产 smoke 与回滚步骤明确。小程序等客户端还需单列预览、真机、质量扫描、上传和审核状态。

## 输出

- 模式、范围、版本、盲区和证据摘要。
- 问题表：ID、证据、契约双方、严重性、影响、修复、验证、负责人、状态。
- 已对齐项与未验证项，避免报告只列问题。
- 决议、条件、残余风险和下一次复核入口。

设计文档是 `CREATED`，读取到的代码/日志是 `OBSERVED`，运行门禁通过才是 `VERIFIED`。

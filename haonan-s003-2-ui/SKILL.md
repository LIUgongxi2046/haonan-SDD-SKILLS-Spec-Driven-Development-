# Haonan S003-2 UI

## 定位

把整套产品视为一个连续世界，而不是若干张孤立页面。优先保证范围可追溯、页面和状态完整、视觉一致、资产真实且可交付。

- **阶段**：S003-2，高保真 UI 设计与交付。
- **上游**：可承接 `$haonan-s002-prd`、`$haonan-s003-1-prototype`、现有代码或任意一种可用输入；不要求上游必须齐全。
- **下游**：向 `$haonan-s004-hld` 提供体验与端侧约束，向 `$haonan-s005-4-lld-front` 提供 Token、组件、状态和资产契约，并向 `$haonan-s006-review`/`$haonan-s007-planner` 提供可追溯的视觉验收基线；获授权后可直接实施前端视觉层。
- **边界**：不替代产品需求决策、后端契约或前端 LLD；不得仅凭视觉稿发明后台规则。

多端项目把每个目标端视为独立验收面。共享品牌系统不代表页面结构完全相同；小程序原生导航、安全区、胶囊按钮、TabBar 与 H5 浏览器栏必须分别设计和核查。

## 工作模式

先识别模式，并在交付说明中标记：

1. **DESIGN**：默认模式。只生成设计规范、页面稿、状态稿、Token、资产与清单，不修改代码。
2. **AUDIT**：盘点现有页面、设计稿或资产，输出覆盖率、缺口和修复优先级。
3. **IMPLEMENT**：只有用户明确要求“落地、重构、修改代码”后启用；先检查仓库约束，再修改和验证。

用户说“先不动代码”时始终保持 DESIGN。若用户已选定视觉方案，继承该方案，不重新发散。

## 输入与事实源

接受以下任一输入独立启动：

- **代码/路由**：以真实路由、页面目录、导航、弹窗和条件分支为事实源。
- **PRD**：以角色、业务目标、功能、用户故事、权限和验收条件为事实源。
- **原型/截图**：以可见入口、层级、控件、交互线索和页面关系为事实源。
- **混合输入**：按“代码真实现状 > 明确 PRD > 已确认原型 > 合理推导”处理冲突。

把信息标为 `EXPLICIT`、`INFERRED`、`UNKNOWN`。合理推导必须进入假设清单，不得冒充既有事实。只有缺失信息会实质改变范围、品牌方向或代码安全时才提问。

只有 PRD 或只有原型时，读取 [references/prd-and-prototype-inputs.md](references/prd-and-prototype-inputs.md)。

## 必读路由

- 确定视觉方向、Token、组件和 IP 体系时，读取 [references/visual-system.md](references/visual-system.md)。
- 盘点路由、页面、流程或状态覆盖时，读取 [references/coverage-and-states.md](references/coverage-and-states.md)。

## 工作流

### 1. 建立范围基线

1. 识别输入模式、目标端、交付格式、品牌约束和代码授权状态。
2. 建立 `route-design-map.csv` 或 `screen-design-map.csv`。
3. 建立 `assumptions-and-open-questions.md`，记录来源、冲突、假设和阻塞项。
4. 为每个核心任务流确定开始、关键决策、失败恢复和完成节点。

### 2. 锁定视觉方向

- 用户未选风格时，给出 2–3 个差异明确的方向，说明关键词、配色、材质、IP、适用场景和风险，等待选择。
- 用户已有参考或已选方案时直接继承。
- 先完成一张视觉母版：核心页面、关键组件、主要状态和 IP/资产样例；确认后扩展。
- 可参考竞品的信息层级和反馈机制，但不得复制商标、角色或专属资产。

### 3. 建立设计系统

至少定义：

- 语义化颜色、字体、8pt 间距、安全边距、最大内容宽度和安全区。
- 圆角、描边、阴影、材质、动效强度和响应式断点。
- 按钮、输入、Tab、列表、卡片、导航、弹窗、进度、Toast 和反馈组件的状态。
- 可访问性：文本对比度、键盘焦点、语义标签、触控尺寸、减少动态效果。
- IP、场景、插画和图标的角色一致性、使用场景与禁用方式。

优先建立组件变量和复用结构，再扩展页面。不要逐页复制后产生视觉漂移。

### 4. 分批完成页面与状态

按范围基线推进：

1. 核心体验：登录、首页、主任务、关键结果页。
2. 一级导航模块和核心列表。
3. 二级分类、详情、搜索、计划和个人中心。
4. 边缘页面：协议、设置、历史、管理页。
5. 系统状态：加载、空、错误、权限、断网、确认、删除、反馈、完成、锁定和重试。

多端批次同时检查：顶部导航是否避让系统区域，背景是否延伸到约定安全区，遮罩是否覆盖正确容器，弹窗是否只出现一次，底部导航选中态/未选中态是否完整，浅色背景文字是否满足对比度。

每批执行一致性门禁；不得以页面不重要为由降低完成度。

### 5. 生成真实视觉资产

- 有源资产时优先裁切和适配；缺少品牌性资产时使用当前可用的图像生成能力。
- 标准功能图标优先使用同一图标库；品牌图标、IP 和场景插画提供独立资产。
- 先测量槽位和比例，再生成或裁切；禁止拉伸、低清放大和不匹配裁剪。
- 不用 Emoji、文字符号、空白框或临时 CSS 图形冒充最终品牌资产。
- 小程序关键图标优先使用可打包的本地图片或已验证组件方案；字体图标、运行时远程资源和条件编译路径必须在预览包中实测。
- 记录资产来源、生成方式和使用限制；不得把含真实个人信息的数据放入设计稿或外部生成服务。

### 6. 交付与审计

默认交付目录遵循 [references/delivery-and-slicing.md](references/delivery-and-slicing.md)，至少包括：

- 页面或路由映射、假设清单、设计系统和 `tokens.json`。
- 全页面设计稿、核心状态稿、真实资产和预览板。
- `asset-manifest.csv`、`page-asset-map.csv` 和 `ui-audit.md`。
- 用户明确要求且能力可用时，补充可编辑 Figma 文件或 PDF；能力不可用时明确标记限制。

运行：

```bash
python3 scripts/audit_ui_delivery.py <delivery-root>
```

该脚本只验证结构、清单、JSON 和文件引用，不代替人工视觉审核。

### 7. 可选代码落地

仅在 IMPLEMENT 模式执行：

1. 读取仓库说明、技术栈、测试命令和现有未提交改动。
2. 先接入 Token、字体、主题和真实资产，再提炼共享组件。
3. 逐路由替换视觉层，保留接口、数据结构、状态管理和业务规则。
4. 使用增量修改，不覆盖用户的无关变更。
5. 运行格式化、类型检查、测试、生产构建和资产引用审计。
6. 建立“所有修改页面 × 目标端 × 关键状态”的截图矩阵；至少覆盖导航、弹窗、加载、结果和底部栏状态。
7. 有浏览器或目标平台预览能力时，在相同视口对比参考稿与实现截图；否则标记 `VISUAL_VERIFICATION_BLOCKED`。

## 完成定义

只有满足以下条件才可声明完成：

- 范围基线中的必需页面和流程节点缺失数为 0；推导范围单列。
- 每个核心流程的必要状态都有设计或明确的不适用说明。
- 页面使用统一 Token、组件和可访问性规则。
- 所有可见定制配图与图标都有真实文件，清单引用缺失为 0。
- 设计规范、页面稿、状态稿、资产、清单和自查报告齐全。
- IMPLEMENT 模式下生产构建通过；声称视觉一致时已完成浏览器对照验收。

## 汇报规范

- 先报模式、结论、覆盖数量、缺失数量和阻塞项。
- 使用 `PLANNED`、`CREATED`、`OBSERVED`、`VERIFIED`、`BLOCKED` 标记状态。
- 不使用“基本完整”“应该都包含”“像素级还原”等无法核查的表述。
- 不声称页面、切图、构建或视觉验收完整，除非已执行相应盘点和验证。

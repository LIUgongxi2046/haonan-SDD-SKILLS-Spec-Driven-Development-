## 🔄 Progressive Output (五步质量防线与交付生成法)
按测试资产、工程、AI 和报告四阶段执行，完整授权下持续推进。阶段确认仅适用于用户要求的交互评审。以下矩阵描述测试设计，实际通过结论必须来自执行证据。

各阶段按当前请求采用相应执行模式，阶段启动条件沿用测试接收中的用户决定：

- `PLAN`：需求与风险覆盖、验收动作、测试数据和门槛。
- `IMPLEMENT`：按授权创建或更新测试与测试配置。
- `EXECUTE`：执行检查，保留原始结果和环境身份。
- `ACCEPTANCE`：检查全部承诺动作和跨模块结果是否满足。
- `REPORT`：根据已读取的真实结果报告证据范围。

- **第一阶段 (Test Assets: 测试资产输出)**：**[核心交付]** 基于上游产出物，直接输出 **【第 1 节：详细的测试用例矩阵与异构测试数据集】**（必须穷举正常与异常边界，并提供 JSON/Markdown 数据样本）。询问：“*全场景边界测试用例与 Mock 数据集已生成，是否作为研发阶段的验收基准？*”
- **第二阶段 (Engineering: 传统工程防线)**：输出 **【第 2 至 3 节：单元测试、接口规范与 UI 自动化测试策略篇】**。询问：“*前后端工程测试桩已确立，确认后我将进入 AI 算法专属评测设计。*”
- **第三阶段 (AI Evals: 算法与智能体评测)**：输出 **【第 4 至 5 节：大模型 Evals、Agent 状态机与 RAG 召回测试篇】**。询问：“*认知引擎与知识库评测逻辑已锁定，确认后我将输出 CI/CD 与自愈机制。*”
- **第四阶段 (Report & Healing: 报告交付与自愈)**：**[核心交付]** 输出 **【第 6 至 7 节：AI 自动修复 (Auto-Healing) 机制与详细的标准测试报告模板】**。

各阶段保留完整承诺及用例资产，历史有效内容经核实后继续维护，无须因阶段切换重复生成。执行安排按检查影响和证据适用性确定，进入 S009 或出现新 commit 本身不能证明全部业务检查失效。用户要求当前完整验收、已明确的 S009 独立执行、发生变化或缺少有效证据的检查仍须实际运行。跨基线复用仅在 S000 配套工具实施并验证后使用，当前限制及判定流程见 [业务验收与证据审查](references/acceptance-workflow.md)。

测试策略根据业务影响、实际使用频率、变更范围、历史缺陷和已批准质量要求安排顺序、测试类型及自动化方式，写明依据。所有必需验收保持完整，优先级不改变通过标准，不因期限或用例数量目标省略正常、异常、边界和对抗要求。用例设计检查在本批用例形成后及执行前进行，有效结果按影响复用；检查本身不要求重新生成整套资产。S008 可以在开发阶段使用这些设计方法和已有用例，S009 的启动时间继续遵守整批开发交付条件。

### 1.2 详细的异构测试集生成 (Detailed Test Datasets)
输出实际数据集及 Schema，记录来源、许可、版本、业务分层和复核人。使用项目规定的数据目录；禁止以合成结果冒充真实服务响应。

数据准备沿用用户批准的数据来源及模拟范围，记录具体值或受控文件引用、目标用例、预期触发条件、关联记录与使用环境。资料中的样例仅帮助选择类别，合法性由当前项目规则确定；不能把未执行表达式或描述占位当作已准备的输入。需要生成数据时使用项目已有成熟工具及获准方法，记录工具版本和适用的随机种子；种子不能代替实际数据版本与校验。

- **合法数据**：核验格式、边界、精度、唯一性、关联范围及状态和时间顺序，确保全部必要前置有效。
- **异常数据**：明确刻意违反的规则和预期拒绝结果，保持到达目标校验所需的其他条件有效。多项异常组合明确预期处理顺序或规则依据；被前置校验拒绝不能证明后续目标分支已经覆盖。
- **边界有效性**：实际计算字符串长度、数值精度、日期合法性及文件大小；字符按项目规定的字节、码点或其他单位计量，时间记录时区与比较规则，不能直接采信样例注释。
- **关联一致性**：按实际依赖准备实体，检查外键、组织与用户范围、业务计算、状态及先后时间；必要前置通过正式接口建立的要求保持不变。故意构造关联异常时明确目标断言。
- **生命周期与隔离**：登记准备、使用、清理范围及唯一负责人。共享数据重置须核实其他执行者使用关系及受影响证据，不因进入新轮回归自动重置全部环境。联系方式及外部通知使用获准测试接收方和隔离配置，不能凭随机值或命名前缀认定不会影响实际用户。

数据检查保存实际规则、结果及受影响用例。数据不满足目标条件时修正数据或准备方式，并按影响复验；不能修改产品预期使错误前置通过。受控来源、凭据和敏感信息使用引用方式，普通用例与报告不包含秘密值。

## 2. 工程部分：单元与接口测试 (Unit & API Testing)
- **单元测试 (Jest/Vitest)**：测试状态机处理 `StreamChunk` 的原子函数；测试业务逻辑层的计算公式与脱敏 Filter。
- **接口测试 (Supertest)**：强制引入 `zod` 在测试期拦截请求体。在 CI 环境临时拉起 PostgreSQL 容器 (Testcontainers)，测试事务回滚的原子性。

接口用例记录实际方法与路径、角色、必要 Header 名称、请求参数和 Body 或受控数据引用、HTTP 与业务状态、响应字段及适用持久化和缓存断言；没有 Body 的接口说明不适用。空值、缺失、枚举、精度、序列化、幂等和并发根据当前规范设计，状态码及业务结果不套用示例。凭据仅引用安全配置，接口成功响应不能替代业务结果重读。

自动化选择考虑重复执行频率、断言稳定性、可观察结果、准备成本及维护成本。功能在变化中仍执行适用的自动化行为检查，不能以界面未稳定为由跳过必要验证；手工检查在已有授权与工具条件内保留可核查步骤和实际结果。测试层次与数量按业务风险及检查对象安排，不为固定比例制造用例。

## 3. 算法部分：大模型评估与提示词工程 (AI Evals)
*(应对非确定性，拒绝玄学调优，用 CI 跑分代替人工直觉)*
- **Prompt 回归评估 (Promptfoo)**：针对 System Prompt 调整或模型基座切换，运行 50 条边界 Query 测试，验证语义相似度与 Token 消耗。
- **越狱防御验证 (Jailbreak Evals)**：输入恶意角色劫持 Prompt，通过自动化脚本验证其是否被 Llama-Guard 等网关成功拦截。

## 4. 算法部分：Agent 状态机与 RAG 召回测试
- **Agent 路径覆盖**：使用实际模型、真实工具和获准输入执行成功、错误、取消与人工审核路径，核查状态转换和终止；未实际触发的路径保持未验证。
- **RAG 质量跑分 (Ragas)**：
  - **Faithfulness (忠实度)**：大模型生成的回答，必须 100% 能够在其引用的 Context 中找到依据（目标 `> 0.95`）。
  - **Context Precision (召回精度)**：基于 `golden_dataset.json`，判定前 5 个 Chunk 是否包含解决问题的核心片段。

## 5. 工程部分：端到端与防白屏测试 (E2E UI - Playwright)
- **主链路 E2E 测试**：模拟登录 -> 上传病历 -> 触发解析 -> 检查 Markdown 渲染与打字机特效 -> 验证引用角标可点击。
- **连接中断检查**：在获准测试环境中中断真实 SSE 连接，记录实际请求与结果，验证错误提示、保留内容、重试预算及恢复状态；不使用伪造响应证明真实服务通过。
- **高保真页面验收**：按批准页面映射和原型版本验证结构、布局、尺寸、间距、字体、颜色、图标、控件、弹窗及适用状态，接收 S008 开发中检查及差异修正证据。视觉比较按现有授权在相同浏览器、视口、字体和数据状态执行，覆盖完整页面及适用状态；图像差异指标仅辅助判断。源码、DOM、计算样式、行为和视觉分别记录结果，未执行视觉比较不能宣称视觉一致；存在未解决差异时保留页面未验收事实。
- **页面回归范围**：共享组件、CSS、Token、字体、资源、数据内容或接口变化时，根据实际使用关系检查受影响页面及状态。未受影响且证据仍有效的部分按复用规则接收，不因单页修复重复全部页面测试；原型变更须依据有效设计决定，不能改写参考图以接受当前实现。

## 6. CI/CD 流水线与 AI 自愈机制 (Auto-Healing)
### 6.1 流水线运行命令与卡点阈值 (CI Gates & Commands)
S009 实际执行获准的测试并提供命令与证据；CI YAML 由 S011 DevOps 集成。工具按当前工程选取，所有阈值记录来源，不能把某个工具的总分直接标记为另一种指标。
- **单元与接口测试**：执行 `npm run test:ci`，通过率必须达到 100%。
- **Evals 检查**：执行项目实际配置的 Promptfoo 与 RAG 评测命令，分别记录 Prompt 回归和 Faithfulness、Context Precision 的评分器、版本、阈值及结果；未达到批准标准时返回失败并保留报告。
- **UI 端到端测试**：执行 `npx playwright test`，输出测试报告归档。

上述命令依据实际工程选用；本次执行范围由批准检查计划和变更影响确定，不能把示例命令当作每次都需重新运行全部检查的要求。代码、检查、直接及间接依赖、配置、数据或环境变化时复验对应范围；共同检查满足输入、环境、定义和责任条件时由唯一执行者运行，其他使用方引用证据并保留专属断言。S011 接入相同检查选择与证据规则，规则和工具未具备时不得声称 CI 已支持跨基线复用。

缺陷反馈包含缺陷 ID、原验收 ID、复现入口、版本、输入、预期、实际及原始证据。主 Agent 分配 S008 修复，S008 提交修改及影响范围，S009 核实后复验失败项和受影响流程。自愈动作不能降低断言或自行改变业务预期；未受影响的隔离检查继续执行，受影响批次待修复版本确认后重新执行必要检查。首次整批开发启动条件不要求每次修复重新启动全部开发流程。

主 Agent 按 [S000 持续交付流程](../haonan-s000-pmp/references/delivery-workflow.md) 协调依赖、环境和责任，S009 保留独立预期与复验结论。开发完成、指导已执行和缺陷关闭分别以对应证据判断。验证工具发生修改时核查实际调用方及当前结果，不从配套设计推断工具已支持；具体接收按 [验收流程](references/acceptance-workflow.md) 执行。

每批用例形成后检查覆盖、预期依据、触发有效性和可执行性；执行前确认当前数据、权限、环境、步骤与完成条件可用。问题关联原用例与负责人，在对应范围修正后复核，其他可执行检查继续。用例检查通过只表示测试资产满足相应准备条件，不能登记产品测试通过；不以固定评分、步骤数或修复轮数替代必需验收。已有检查结果有效时复用，数据或步骤变化时检查其影响范围。
